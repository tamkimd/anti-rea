# Workflow and current state

Anti-REA uses a shared versioned record model:

```text
discovered -> baselining -> awaiting_decision -> preparing -> executing -> verifying
```

Failure, cancellation, blocker, and renewed-decision states are explicit. The current record core validates these transitions and stores run state with compare-and-swap. The CLI and MCP can record a target, baseline reference, plan, client-transmitted decision, and run authorization.

## Requirements checklist before a baseline

After discovery, show the user a requirements checklist for the release target, build command, artifact paths, expected valid and error behavior, public interfaces, available runtime/toolchain, and behavior, performance, and integrity checks. Mark each item confirmed, missing, or unverified. `anti-rea doctor` checks Anti-REA prerequisites; it does not infer target build needs or install tools. For a Flutter Android target, run `anti-rea flutter-android-probe` or MCP `probe_flutter_android_environment` to report host Flutter, Android SDK, license, Flutter-configured Java runtime, build, and connected-device readiness without accepting licenses or installing tools. This is a host toolchain check; it does not verify the selected project, app build, signing, or app/device behavior. Use a registered readiness probe for other supported lanes; otherwise state that platform requirements are unknown and ask for exact build and verification inputs. Do not capture a baseline until the user supplies a concrete target, build command, and artifact selection.

The CLI and MCP perform bounded, read-only manifest-based discovery and can capture a BEFORE build by executing an explicit command, hashing selected artifacts, and retaining bounded output. WASM discovery parses bounded version-1 import/export sections, checks standard section uniqueness and order, and binds metadata to the inventoried artifact hash and owning component; malformed headers, selected import/export sections, unsupported descriptor types, oversized modules, and capped scans remain incomplete. Other section payloads are not validated, and parsing does not verify module semantics or runtime bindings. In a monorepo, each artifact is assigned to the nearest recognized manifest directory; artifacts without a manifest ancestor are listed as unassigned. This is a path-based hint, not a verified build graph. Baseline capture optionally accepts a behavior argv with exactly one `{artifact}` for one JavaScript artifact; it runs against a private project copy and binds the copy identity, bounded output hash, and command into the baseline. Baseline and execution behavior copies omit excluded dependency/generated trees and discovered symlinks, so checks requiring them may be blocked; host-run execution behavior commands can still write outside a copy. Baseline build and optional behavior commands using `node`, `npm`, or `npx` default to the pinned offline Docker profile, with only the private snapshot mounted writable and external absolute argv path tokens rejected. The Docker daemon is trusted and the snapshot has no live disk quota; `ANTI_REA_NODE_SANDBOX=host` explicitly selects unsandboxed host execution. Artifact hashing fails closed when safe directory-relative opens are unavailable. `recommend` / `create_plan` can suggest candidate-tree exclusion for a baseline-hashed source map when a private build snapshot exists, manual release review without a snapshot, or a BLA candidate for a baseline-hashed JS file. Source-map acceptance proves only that the selected map is absent from the private candidate tree and all other inventoried files match the baseline. A behavior command must match the captured command and is attached only to the artifact measured by the BEFORE run. `submit-plan` / `submit_plan` bind the plan to the matching run and place it at the user decision checkpoint. CLI users can run `choose RUN_ID STORE` to review the complete action trade-offs and record one explicit choice; MCP clients collect the choice in conversation and submit the plan-bound decision. After an approved selection, `execute-plan` / `execute_plan` can run either the BLA JavaScript adapter or source-map candidate adapter into private state; only BLA requires a BLA runtime. The argv behavior check compares the captured BEFORE output with successful source and candidate runs on paired private copies, all with identical bounded stdout. Optional `e2e_behavior` requires a successful pinned browser report captured during baseline on a private snapshot. The report, snapshot identity, runtime, and test scope are hash-bound to the baseline; after approval, execution reuses that immutable BEFORE report and runs the candidate snapshot only. A failed baseline browser check prevents baseline creation. The check validates raw report hashes, test scope, runner identity, and server cleanup. Browser assertion failures retain reports and reject/quarantine the candidate; the fixture-compatible config/test contract is not a general browser adapter, and project test/config code runs outside an OS sandbox. REA compares baseline-matched snapshots with run-bound evidence. MCP `start_baseline_async` and `execute_plan` schedule long-running work for `get_run` polling; `cancel_run` cleans up active baseline and execution process trees (POSIX process groups; Windows Job Objects for baseline and REA runners, not yet runtime-tested on Windows) and can close a completed baseline awaiting plan submission while retaining its immutable evidence; execution cancellation also discards the incomplete candidate; normal interpreter shutdown also requests worker cancellation, cleans up command process trees through POSIX process groups or Windows Job Objects, and joins workers; Windows Job Object behavior remains unverified on Windows. Worker state is process-local and does not survive a crash or forced termination. Canceling a verifying run hash-checks and quarantines its candidate with a rollback record. Reports are retained. `resume RUN_ID NEW_RUN_ID STORE` / `resume_run` creates a fresh attempt only after revalidating source and baseline artifact hashes, the approved plan and decision, and any prior evidence. It supports single-file BLA JavaScript and source-map candidate runs; it refuses stale inputs, active prior candidates, and unverifiable cancellation quarantine, including a changed retained source-map tree. Dependency and generated directories excluded from discovery remain outside its inventory, so review lockfiles and runtime identities separately. CLI baseline capture and the backward-compatible MCP `start_baseline` are synchronous; deployment rollback remains unimplemented. The acceptance gate requires every selected check to pass and validates source-map exclusion, BLA, behavior, and run-bound REA evidence. Failed, unavailable, or semantically invalid required checks automatically produce a rejected, blocked run and quarantine the candidate with retained evidence; record consistency does not prove protection.

For the verified static SPA fixture contract, list every built release file as a repeated `--artifact` (for example HTML, the selected JS bundle, and CSS) and pass its project-owned e2e config/test. Exactly one declared artifact must be JavaScript for the current BLA lane; the source-map lane can separately omit one selected `.map` from a private candidate tree. `--rea-runtime` optionally captures the REA summary before plan selection. This fixture evidence does not establish general framework or server rendered support.

Build-time variability is opt-in because a build command may have external side effects or be costly: CLI `baseline --build-time-trials N` and MCP `start_baseline(build_time_trials=N)` accept 1–5 runs. Additional trials use fresh private copies and retain bounded reports, elapsed times, and artifact hashes; differing artifacts are explicitly reported. One default trial remains a single observation and must not be reported as variability evidence.

The repository tracks implementation status by phase in `AUDIT.md`; that audit is not part of a standalone Skill installation.
