# Flutter Dart obfuscation candidate

Flutter Android baselines use the release build without Dart obfuscation. A plan can then offer `flutter-dart-obfuscation` for the captured APK or AAB. The action is bound to that artifact hash, the captured command, the exact persisted plan, and the user's approved action set.

Execution copies the captured build tree to a private workspace, rebuilds the selected target with `--obfuscate --split-debug-info`, keeps the package under the private candidate store, and retains symbols separately under private state. A successful command is recorded as `built_unverified`. It does not claim the candidate is accepted or protected.

Acceptance requires two externally attached reports: `flutter_aot_comparison` must contain hash-bound raw REA `inspect_dart_aot` output for the baseline and candidate APK, with matching REA runtime identity, complete selected ABI section coverage, and comparable observations. `flutter_android_behavior` must show identical passing behavior cases on the same identified Android target for the exact baseline and candidate APK hashes. The behavior report includes hash-bound APK signature reports, and acceptance independently reruns the captured Android SDK `apksigner` against both APK files. The baseline captures the exact `apksigner.jar` SHA-256; acceptance requires the same jar bytes and build-tools version. The locally verified signer count and certificate digest must match the reports and each other. This establishes signature validity and same-certificate continuity; it does not establish publisher identity or external trust. Signature verification requires the captured Flutter toolchain, Android SDK build-tools, and JDK to remain available. Both checks bind the exact plan, baseline source identity, Flutter/Android toolchain identity, dependency lock hash, candidate APK, and private symbol tree. The package-inspection and Android behavior providers do not yet emit these paired verification records, and pinned REA 6.8.0 cannot inspect the current unified Dart snapshot, so candidate acceptance remains blocked.

REA AOT readiness must be attached to the baseline before a Flutter action can be planned. `anti-rea attach-flutter-aot` creates a new baseline record bound to the exact APK digest and size, selected ABI, raw report hash, and pinned runtime manifest. Missing or unsupported evidence produces an explicit plan blocker, and plan submission independently rejects the blocked plan. The original baseline record remains unchanged.

The pinned REA 6.8.0 runtime does not recognize the unified Dart snapshot exports `_kDartSnapshotText` and `_kDartSnapshotData`; it returns `unsupported_target` for this profile. The Loopweek baseline report records that result. An isolated build of [REA PR #3662](https://github.com/morluto/rea/pull/3662) inspected the exact same arm64 APK with complete structural coverage and partial string-pool coverage; its sanitized result is [here](../examples/loopweek-flutter/evidence/rea-pr3662-aot-candidate.json). The PR remains unmerged and its source-built runtime is not the pinned runtime, so it does not clear Anti-REA's planning gate. A fresh external checkout at the recorded PR head built successfully and passed all 103 Flutter provider tests. A new inspection of the exact local baseline APK reproduced complete structural coverage and partial string-pool coverage; the hash-bound raw result stays outside the repository. Direct Git installation with lifecycle scripts disabled omits the untracked `dist` output. Building and packing the exact checkout externally produced a 9.3 MiB tarball (SHA-256 `8ceb743bd90226b5c28353316841f6a420fbaefc347a86a1b45eb831155f0377`) that installed with scripts disabled; `rea --version` and worker-module import passed. This provides a reproducible candidate package shape, but not a promoted pin: the PR remains unmerged and its build/pack provenance is not yet an Anti-REA dependency workflow. The pinned runtime and planning gate remain unchanged. Keep candidates blocked until a released REA pin is installed, its contracts are reviewed, and the exact artifact passes the pinned workflow. Track [REA issue #3629](https://github.com/morluto/rea/issues/3629).

Release signing identity and trust are also not established by this candidate lane. Flutter obfuscation renames Dart symbols; it does not encrypt resources or prevent reverse engineering. Keep the matching symbol map private and retain the exact release signing, toolchain, and dependency lock inputs for any future comparable build.
