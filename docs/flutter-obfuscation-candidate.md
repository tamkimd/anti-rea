# Flutter Dart obfuscation candidate

Flutter Android baselines use the release build without Dart obfuscation. A plan can then offer `flutter-dart-obfuscation` for the captured APK or AAB. The action is bound to that artifact hash, the captured command, the exact persisted plan, and the user's approved action set.

Execution copies the captured build tree to a private workspace, rebuilds the selected target with `--obfuscate --split-debug-info`, keeps the package under the private candidate store, and retains symbols separately under private state. A successful command is recorded as `built_unverified`. It does not claim the candidate is accepted or protected.

Acceptance requires two hash-bound reports: `flutter_aot_comparison` contains raw REA `inspect_dart_aot` output for the baseline and candidate APK, with matching REA runtime identity, complete selected ABI section coverage, and comparable observations. `flutter_android_behavior` records identical passing cases on the same identified Android target for the exact APK hashes. Its signing references are independently checked by the captured Android SDK `apksigner`; the verifier JAR and build-tools version must match the baseline. The signer count and certificate digest must agree with the reports and each other. This establishes signature validity and same-certificate continuity, not publisher identity or external trust. Signature verification requires the captured Flutter toolchain, Android SDK build-tools, and JDK to remain available. Both checks bind the plan, baseline source identity, Flutter/Android toolchain, dependency lock, candidate APK, and private symbol tree.

The Foodie Flutter 2.5.3 example completed this workflow: pinned REA 6.8.0 reported complete structural coverage for baseline and obfuscated candidate APKs; both APKs verified with the same signer certificate; and a cold launch passed on the same Android 16 arm64 emulator with identical screenshots. The behavior claim is intentionally narrow: only app launch was repeated, not checkout, network, payment, or a broad regression suite. See the sanitized [Foodie evidence summary](../examples/flutter-foodie/evidence-summary.json). APKs, raw reports, screenshots, and split-debug symbols remain outside the repository. This example does not claim that obfuscation prevents reverse engineering.

REA AOT readiness must be attached to the baseline before a Flutter action can be planned. `anti-rea attach-flutter-aot` creates a new baseline record bound to the exact APK digest and size, selected ABI, raw report hash, and pinned runtime manifest. Missing or unsupported evidence produces an explicit plan blocker, and plan submission independently rejects the blocked plan. The original baseline record remains unchanged. Both the published [Foodie Flutter 2.5.3 APK](../examples/flutter-foodie/README.md) and a fresh source build pass this REA 6.8.0 structural snapshot gate; neither result alone establishes candidate acceptance.

The pinned REA 6.8.0 runtime supports the legacy split VM/isolate snapshot profile used by the published Foodie Flutter 2.5.3 APK. It does not recognize the unified Dart snapshot exports `_kDartSnapshotText` and `_kDartSnapshotData`; it returns `unsupported_target` for that profile, as recorded for the Loopweek Flutter 3.47.8 rebuild. An isolated build of [REA PR #3662](https://github.com/morluto/rea/pull/3662) inspected that exact arm64 APK with complete structural coverage and partial string-pool coverage; its sanitized result is [here](../examples/loopweek-flutter/evidence/rea-pr3662-aot-candidate.json). The PR remains unmerged and its source-built runtime is not the pinned runtime. A fresh external checkout at the recorded PR head built successfully and passed all 103 Flutter provider tests. A new inspection of the exact local baseline APK reproduced complete structural coverage and partial string-pool coverage; the hash-bound raw result stays outside the repository. Direct Git installation with lifecycle scripts disabled omits the untracked `dist` output. Building and packing the exact checkout externally produced a 9.3 MiB tarball (SHA-256 `8ceb743bd90226b5c28353316841f6a420fbaefc347a86a1b45eb831155f0377`) that installed with scripts disabled; `rea --version` and worker-module import passed. This provides a reproducible candidate package shape, but not a promoted pin: the PR remains unmerged and its build/pack provenance is not yet an Anti-REA dependency workflow. Flutter candidate acceptance still requires paired behavior, signing, and comparable BEFORE/AFTER evidence. Track [REA issue #3629](https://github.com/morluto/rea/issues/3629).

Release signing identity and trust are also not established by this candidate lane. Flutter obfuscation renames Dart symbols; it does not encrypt resources or prevent reverse engineering. Keep the matching symbol map private and retain the exact release signing, toolchain, and dependency lock inputs for any future comparable build.
